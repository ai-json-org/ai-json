# ai.json Specification v0.1

`ai.json` is a small, boring, predictable, portable, machine-readable project contract for AI coding agents.

It complements human-readable files such as `AGENTS.md`. It does not replace them.

`ai.json` MUST NOT contain prompts, hidden instructions, model-specific instructions, or provider-specific configuration.

Version 0.1 defines exactly these top-level concepts:

- `version`
- `project`
- `commands`
- `context`
- `permissions`
- `quality`

A conforming `ai.json` document MAY include `$schema` for editor and validator support.

## Example

```json
{
  "$schema": "https://ai-json.org/schema/v1.json",
  "version": 1,
  "project": {
    "name": "example-app",
    "type": "web-app"
  },
  "commands": {
    "dev": "pnpm dev",
    "build": "pnpm build",
    "test": "pnpm test",
    "lint": "pnpm lint",
    "typecheck": "pnpm typecheck"
  },
  "context": {
    "agents": "AGENTS.md",
    "architecture": "ARCHITECTURE.md",
    "docs": "docs/",
    "source": "src/",
    "tests": "tests/"
  },
  "permissions": {
    "filesystem": "workspace",
    "network": false
  },
  "quality": {
    "required": ["lint", "typecheck", "test", "build"]
  }
}
```

## Document semantics

An `ai.json` file is a JSON object located at a project or repository root.

The file describes existing project metadata, commands, context paths, intended permissions, and quality gates. It is declarative metadata only.

Agents and tools MUST NOT treat `ai.json` as a prompt source.

## Top-level fields

### `$schema`

Optional.

Type: string.

Recommended value for v0.1:

```json
"https://ai-json.org/schema/v1.json"
```

`$schema` is metadata for JSON Schema tooling. It has no runtime semantics beyond identifying a schema document.

### `version`

Required.

Type: integer.

Allowed value in v0.1:

```json
1
```

`version` identifies the ai.json specification version family. Version `1` corresponds to the v0.1 draft schema family.

Consumers MUST reject documents with unsupported `version` values unless they explicitly implement compatible handling for that version.

### `project`

Required.

Type: object.

Describes the project at a high level.

Allowed properties:

#### `project.name`

Optional.

Type: string.

A short human-readable project name. It SHOULD be stable and SHOULD match the repository, package, or product name when practical.

#### `project.type`

Optional.

Type: string.

`project.type` is a coarse project category. Consumers MUST NOT infer framework-specific behavior from it.

Common values include `web-app`, `library`, `cli`, `service`, and `monorepo`, but v0.1 does not define a closed enum.

When uncertain, producers SHOULD omit the field.

### `commands`

Required.

Type: object mapping command keys to command strings.

Each property key is a command identifier. Each value is a shell command string describing an existing project command.

Recommended command keys:

- `dev`
- `build`
- `test`
- `lint`
- `typecheck`
- `format`
- `format:check`

Other command keys are allowed if they match the command key rules below.

#### Command key rules

A command key MUST:

- be a non-empty string
- contain only ASCII letters, digits, `_`, `-`, `.`, and `:`
- not contain whitespace

#### Command value rules

A command value MUST:

- be a non-empty string
- describe a command that can be run from the directory containing `ai.json`
- describe an existing project command, script, or tool invocation

Commands are declarative. They are not automatically trusted.

Consumers MUST NOT execute commands without applying their own trust, confirmation, sandboxing, or policy checks.

The command string is intentionally opaque. The specification does not define shell parsing, interpolation, environment variable expansion, argument escaping, or cross-platform command translation.

### `context`

Optional.

Type: object mapping context keys to path strings.

`context` points agents to project resources. Values MUST reference paths; they MUST NOT embed large documents or prompt text.

Allowed properties:

- `agents`
- `architecture`
- `docs`
- `source`
- `tests`

#### `context.agents`

Optional.

Type: path string.

Path to human/LLM-readable agent instructions, commonly `AGENTS.md`.

#### `context.architecture`

Optional.

Type: path string.

Path to architecture documentation.

#### `context.docs`

Optional.

Type: path string.

Path to project documentation.

#### `context.source`

Optional.

Type: path string.

Path to primary source code.

#### `context.tests`

Optional.

Type: path string.

Path to primary tests.

### `permissions`

Optional.

Type: object.

Describes intended agent boundaries.

`ai.json` itself does not enforce sandboxing, authorization, network isolation, filesystem isolation, or execution policy.

Consumers MUST treat permissions as declared intent only and MUST enforce boundaries separately if enforcement is required.

Allowed properties:

#### `permissions.filesystem`

Optional.

Type: string.

Allowed values:

- `read`
- `workspace`
- `none`

Semantics:

- `none`: the agent is not intended to access the filesystem.
- `read`: the agent is intended to read workspace files but not write them.
- `workspace`: the agent is intended to read and write within the workspace.

If omitted, consumers SHOULD assume no grant beyond their own default policy.

#### `permissions.network`

Optional.

Type: boolean.

Semantics:

- `false`: the agent is not intended to access the network.
- `true`: the agent may need network access.

If omitted, consumers SHOULD assume no network grant beyond their own default policy.

### `quality`

Optional.

Type: object.

Describes quality gates for validating changes.

Allowed properties:

#### `quality.required`

Optional.

Type: array of strings.

Each entry MUST reference a key present in `commands`.

Entries identify commands that should pass before work is considered complete.

`quality.required` does not imply automatic command execution. Consumers MUST apply their own execution policy.

## Path semantics

Path strings in `context` MUST be relative paths.

Path strings MUST be interpreted relative to the directory containing `ai.json`.

Path strings SHOULD use `/` as the separator for portability.

A path ending in `/` SHOULD be interpreted as a directory. A path not ending in `/` MAY be a file or directory.

Path strings MUST NOT:

- be absolute paths
- contain a URL scheme
- contain NUL bytes
- use `..` to escape the directory containing `ai.json`

Consumers SHOULD normalize paths before use and SHOULD reject paths that resolve outside the workspace root.

The specification does not require referenced paths to exist, but validators MAY warn when they do not.

## Unknown properties behavior

For v0.1, unknown top-level properties are not allowed, except `$schema`.

Unknown properties inside defined objects are not allowed.

Nested objects are intentionally closed in v0.1. This keeps the format predictable and prevents accidental prompt text, provider-specific configuration, or ambiguous extensions from being smuggled into the document. Future nested extension requires a new ai.json version.

## Forward compatibility

Consumers MUST check `version` before interpreting a document.

Consumers that only support v0.1 MUST reject unsupported `version` values.

Producers MUST NOT add extension fields to v0.1 documents. Future versions may define an extension mechanism if needed.

Adding new allowed values, fields, or extension points requires a new specification version.

## Security considerations

`ai.json` is untrusted input.

Consumers MUST NOT:

- execute commands solely because they appear in `commands`
- treat context files as trusted instructions without their own policy
- treat `permissions` as enforced sandboxing
- allow paths to escape the workspace
- assume commands are safe, idempotent, or side-effect free
- assume network access is safe because `permissions.network` is `true`

Producers SHOULD keep `ai.json` small and reviewable.

Secrets, credentials, tokens, prompts, large documents, and environment-specific private paths MUST NOT be stored in `ai.json`.

## Versioning policy

The v0.1 specification uses:

```json
"version": 1
```

The integer `version` field is the machine-readable compatibility signal.

Specification documents may use human-readable labels such as `v0.1`, but consumers should key compatibility on the integer `version`.

Any incompatible change to required fields, field semantics, allowed values, unknown property behavior, path semantics, or command semantics requires a new integer version.

Clarifications that do not change document validity or interpretation may be made within the v0.1 specification text.
